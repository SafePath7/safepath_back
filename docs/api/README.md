# 기능별 API 브랜치

두 기능 브랜치는 `develop`에서 출발한 동일한 인증·오류 처리 공통 커밋을 포함합니다. 서로의 기능 커밋에 의존하지 않으므로 각각 `develop`을 대상으로 검토할 수 있습니다. 공통 커밋은 같은 이력을 공유합니다.

| 브랜치 | 구현 범위 | 상세 문서 |
|---|---|---|
| `feature/guardian-registration-api` | 보호자 요청·수락·거절·해제·중지·권한 수정·확인 7개 | 해당 브랜치의 `docs/api/guardian-registrations.md` |
| `feature/risk-event-api` | 위치 저장·조회, 위험 이벤트 생성·상태 수정, 미디어 관리 7개 | 해당 브랜치의 `docs/api/risk-events.md` |

인증 연결 필터, `FirebaseIdTokenVerifier` 인터페이스, 현재 사용자 조회, 오류 응답과 환경변수 관리 규칙은 공통입니다. 실제 Firebase 토큰 검증 구현체는 별도 담당 모듈이 필요하며, 없으면 요청은 401로 거절됩니다. 공통 코드 자체는 별도 API를 추가하지 않습니다.

위험 이벤트 브랜치는 기존 `guardian_registrations`에서 수락 상태와 위치 조회 권한을 읽습니다. 보호자 등록 API를 포함하지 않으며 보호자 브랜치 없이도 기존 연결 데이터를 사용할 수 있습니다. 요청·응답 형식과 기존 V1 테이블 정의는 그대로입니다. V2 위치 테이블은 위험 이벤트 브랜치에만 포함합니다.

## 검증

Docker PostgreSQL을 실행하고 로컬 DB 계정을 프로세스 환경변수로 전달한 뒤 `gradlew.bat build`를 실행합니다. 테스트는 클래스별 임시 스키마에 해당 브랜치의 마이그레이션을 적용하므로, 로컬 public 스키마에 V2가 이미 적용되어 있어도 V1만 있는 보호자 브랜치를 검증할 수 있습니다. 테스트 후 스키마를 제거합니다. 실제 JWT 서명 검증은 테스트 대역을 사용합니다.

각 브랜치의 통합 테스트는 담당 패키지에 명세의 API 7개가 정확히 등록됐는지 확인합니다. 기능별 테스트 클래스·문서 파일을 분리해 나중에 두 기능을 함께 사용할 때도 테스트가 충돌하지 않게 구성합니다.
